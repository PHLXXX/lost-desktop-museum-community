# Registry architecture

## 双仓库职责

主应用负责创作、下载、复验、安装、更新、回滚和游玩；本仓库只负责源目录、审核记录、确定性构建与静态分发。两者通过 Registry v1 JSON 和 `.ldmcase` 包衔接，不共享数据库。

## 数据流

`catalog/` 经 Schema、路径、截图和案件包校验后生成 `dist/registry/v1`、`dist/packages`、`dist/screenshots` 与无脚本 HTML。客户端只从构建时固定的 Registry URL 读取索引；详情、截图和包路径必须保持同源且位于 registry 根前缀内。安装流程是下载、SHA-256、完整包校验、用户二次确认、IndexedDB 事务写入。更新还会执行存档结构兼容分析并创建回滚包。

## 缓存与离线

客户端将索引与详情缓存到 IndexedDB，先显示缓存再按六小时间隔刷新。社区不可用不影响内置、本地导入和已安装案件；新鲜安装且无缓存时仅社区浏览不可用。

## 信任边界

GitHub PR 历史提供可审计变更；Actions 验证格式与执行风险；维护者可人工精选。客户端不信任来源字段、不执行包内文件、不加载包内远程资源，并在本地再次验证。当前没有独立数字签名。

## 发布顺序

先校验并部署社区 Pages，验证索引、详情、截图、包与哈希；再把真实 Registry URL 配置到主应用 Pages，完成线上安装烟雾测试，最后发布两个仓库的版本。
